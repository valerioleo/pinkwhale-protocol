# Run it yourself

## Requirements

[Foundry](https://book.getfoundry.sh/getting-started/installation) and Node 20+ with
[pnpm](https://pnpm.io). Nothing else. No API keys, no accounts, no testnet ETH.

```bash
git clone https://github.com/valerioleo/pinkwhale-protocol
cd pinkwhale-protocol
git submodule update --init
pnpm install
```

## Tests

```bash
forge test
```

Forty-three tests across five suites, all against a Seaport 1.6 deployed fresh in `setUp()`.
Nothing is forked, so a run is fully offline and deterministic.

| Suite | What it proves |
| --- | --- |
| `test/HappyPath.t.sol` | open then repay, and open then default, for ERC20 principal against ERC721 and ERC1155 collateral |
| `test/Guards.t.sol` | every attack in [Try to break it](/reference#try-to-break-it) |
| `test/Criteria.t.sol` | collection offers and merkle sets, end to end |
| `test/Bundles.t.sol` | multi-item mixed collateral, split repayments, and the two composed |
| `test/Tokens.t.sol` | the faucet mocks: per-token decimals, and random minting into a collection |

## A local deployment

Seaport built from source is 25,229 bytes, which is 653 over the EIP-170 limit. The copy on
mainnet was compiled through the IR pipeline and this one cannot be, because its vendored
source predates memory-safe assembly annotations and `viaIR` dies with "stack too deep". Local
anvil needs the limit raised. Live networks do not, because there Pinkwhale registers the
canonical Seaport 1.6 instead of deploying its own.

```bash
cp .env.example .env
anvil --code-size-limit 40000
```

In another terminal:

```bash
forge build
pnpm generate         # deployoor reads out/, writes typed deployers
pnpm deploy:anvil
```

Every address lands in `deployments/31337-anvil/<Contract>.json`: plain JSON with the address,
the ABI as deployed, the constructor args, and the compiler settings. Running `deploy:anvil`
again only sends a transaction when a contract's deploy identity moved, since deployoor is
configured `on-change`.

The deployment lives in `scripts/deploy/`, one module per concern: `seaport.ts` registers the
canonical instance or stands up a local one, `pinkwhale.ts` points the protocol at it, and
`tokens.ts` holds the faucet inventory. Chains, transports and signing keys are resolved in
`scripts/clients.ts` and nowhere else.

## A whole loan

```bash
pnpm test:e2e
```

The Solidity suites drive Pinkwhale through Foundry.
[`test/e2e/loanLifecycle.ts`](https://github.com/valerioleo/pinkwhale-protocol/blob/main/test/e2e/loanLifecycle.ts)
drives it through the viem path a frontend would take instead: it mints an NFT and some
currency, signs both creation orders with anvil's default accounts, opens the loan from a third
address, then repays it.

```
>> executeLoan (submitted by a third party)
     loanId            0x4493b118...0c327f6b
     defaultOrderHash  0x928c5bcf...696b5025
     expiry            2026-09-15T15:57:50.000Z
     collateral owner  0x9fE467...  (Pinkwhale)
     borrower balance  110.00 USDC

>> Repay
     collateral owner  0x3C44Cd...  (borrower)
     lender balance    110.00 USDC
     borrower balance  0.00 USDC
```

It stands the contracts up with the same modules `pnpm deploy:*` uses, so there is one
definition of what gets deployed and with which constructor args.

The order building and EIP-712 signing live in
[`scripts/lib/orders.ts`](https://github.com/valerioleo/pinkwhale-protocol/blob/main/scripts/lib/orders.ts).
That file is also what the widgets on the [article page](/) import, so the hashes on screen
there come from the same code that produces orders Seaport accepts.

## Live networks

```bash
pnpm deploy:sepolia
pnpm deploy:base-sepolia
```

Live deployments sign through a **Privy server wallet**, so no deployer key sits on disk or in
CI: fill `PRIVY_APP_ID`, `PRIVY_APP_SECRET`, `PRIVY_ADMIN_WALLET_ID` and
`PRIVY_ADMIN_WALLET_ADDRESS` in `.env`, and give that wallet gas on the target chain. Anvil is
the exception and keeps a raw key, because a local chain should not need an account with a
vendor.

Pinkwhale points at the canonical Seaport 1.6 at
`0x0000000000000068F116a894984e2DB1123eB395`, which is registered into `deployments/` rather
than redeployed.
